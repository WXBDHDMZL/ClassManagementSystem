## 一、P0 — 数据安全（1 条，已复现）

### P0-1 启动时一次瞬时读取异常，自动备份会把空库写满主文件 / `.bak` / 自动备份三处

**位置**
- `lib/services/storage_service.dart:269-276`（`loadData()` 首行 `await dataFilePath` 与 `File(filePath).length()`）
- `lib/providers/app_data_provider.dart:522-535`（`initialize()` 的 `catch` 只换内存数据，未禁止写盘）
- `lib/main.dart:126`（`unawaited(provider.runScheduledBackup())` 无条件执行）
- `lib/providers/app_data/export_backup.dart:71-116`（`performBackup()`）

**触发条件**
`loadData()` 在取数据目录或读文件长度时抛异常（杀软扫描锁文件、OneDrive/同步盘启动瞬间不可用、磁盘瞬时错误、权限被临时收回）。`initialize()` 捕获后把内存换成 `AppData.empty()`，但 `StorageService._mainFileParsable` 仍是默认 `true`（`storage_service.dart:454`）、`_lastWrittenLength = -1`、`_lastWrittenDigest = null`；随后启动自动备份（默认 `BackupFrequency.daily` 且 `backupLastAt=''`，`lib/models/app_settings.dart:235`）立即执行 `saveData(空 AppData)`：
1. `_saveDataNow` 因 `_lastWrittenDigest == null` 走 `_tryLoadFile(filePath)` 兜底，把真实文件判定为“可覆盖”；
2. `AtomicFile.copyAtomic` 把真实内容拷进 `.bak`，然后把主文件写成空库；
3. `performBackup()` 末尾的 `_save()` 再写一次，此时长度/摘要已匹配 → **把空库覆盖进 `.bak`**；
4. 自动备份文件本身也是空库。

**复现（临时探针，已删除）**
mock `path_provider` 让 `getApplicationDocumentsDirectory()` 第一次抛 `PlatformException(code:'boom')`（模拟同步盘瞬时失败），预置 1 条合成记录：

```
PROBE startupNotice = 数据加载失败，现有数据已重置
PROBE 异常后内存记录数 = []
PROBE 自动备份结果 = …\班级管理系统\备份/班级管理系统_备份_20261121_155815.enc
PROBE 稳态主文件字节 = 7340
PROBE 稳态 .bak 字节 = 7328
PROBE 自动备份解出的 JSON 前 120 字 = {"recordsByDate":{},"settings":{"themeMode":2,...
PROBE 重启后记录数 = 0
PROBE 删主文件后 startupNotice = 数据文件损坏，已自动从备份恢复
PROBE 删主文件后记录数 = 0
```

即：**主文件、`.bak`、自动备份三处全部是空库，没有任何 `.corrupt_*` 残留，真实数据不可恢复**。对当前 真实记录（计数已脱敏）真实数据是“一次异常 = 全没了”的级别。

**修复建议**
1. `loadData()` 抛异常时，`StorageService` 必须置“禁止写入”标志（等同 `_mainFileParsable = false` 的语义），让后续 `saveData` 直接拒绝；
2. `main.dart` 在 `provider.startupNoticeIsError` 为真时跳过 `runScheduledBackup()`；
3. `loadData()` 区分“文件不存在 / 解析失败 / 读盘异常”三种结果，读盘异常不得进入“重置为空”分支；
4. `_saveDataNow` 覆盖 `.bak` 前应要求“本次保存的数据来自成功加载”，而不是仅凭长度/摘要。

## 二、P1 — 高优先级（16 条）

### A. 存储与备份

#### P1-1 旧数据包缺 `periods` 键时，整包还原会清空本机自定义时段（已复现）
- 位置：`lib/services/transfer_service.dart:965-976`、`lib/models/app_settings.dart:429`、`lib/providers/app_data/import_restore.dart:526-559`
- 触发：用 V2.6.0 之前导出的数据包（无 `periods` 键）做整包还原，且本机配置了自定义时段。
- 后果：`parsePackage` 缺键时给的是**空列表**而非 `null`；`copyWith(periods: 空列表)` 生效；`restoreFromPackage` 走 `applyCustomPeriods(const [])`，自定义时段被清空，历史记录的时间段列退化为裸 key。
- 依据：同函数里 `weekStart`、`attendanceEnabled`、`attendanceStatuses` 都实现了“缺键=null=保持本机”，只有 `periods` 没遵守（`PackageData.periods` 声明为非空 `List`，`transfer_service.dart:79`）。
- 状态：已用临时探针复现（输出 `RESTORE 分支 = applyCustomPeriods(const []) 清空本机`）。

#### P1-2 数据包缺 `reasons` 键时，整包还原用出厂原因库覆盖用户原因库
- 位置：`lib/services/transfer_service.dart:912-915`
- 触发：旧包无 `reasons` 键（或键类型不对）。
- 后果：`ReasonLibrary.defaults()` 覆盖用户多年维护的原因库，且不可撤销（还原前的自动备份是唯一退路）。
- 修复：与 `periods` 一起改为 `ReasonLibrary?`，缺键保持本机。

#### P1-3 `_tryLoadFile` 把“读盘异常”与“内容损坏”混为一谈，可能用旧 `.bak` 覆盖完好的主文件
- 位置：`lib/services/storage_service.dart:419-434`，影响 `:284-312`
- 触发：杀软/同步盘/网络盘/权限导致 `readAsString` 瞬时失败，但文件本身完好。
- 后果：`loadData` 判定主文件损坏 → 用可能更旧的 `.bak` 覆盖主文件（`AtomicFile.writeString`），且不留原文件副本 → 最近一次保存以来的数据静默回退。
- 置信度：高（静态）。

#### P1-4 `clearAllBackups()` 不校验备份文件前缀，备份路径设错会删除目录下所有 `*.enc`
- 位置：`lib/providers/app_data/export_backup.dart:161-162,168-197`；调用点 `lib/widgets/settings/backup_restore_actions.dart:60-100`
- 触发：用户把备份路径设为“文档”根目录（或任何存放其它 `.enc` 的目录），恢复出厂时勾选“同时清除全部备份与日志”。
- 后果：`_isBackupFile(name) => name.endsWith('.enc') && !name.endsWith('.enc.bak')` 会把该目录下**所有** `.enc` 当成备份删除，包括其它软件的加密文件；备份路径设为数据目录本身时连 `class_management_data.enc` 一起删。
- 修复：改为匹配 `班级管理系统_备份_\d{8}_\d{6}\.enc` 或至少要求文件名以 `backupFilePrefix` 开头。

### B. 记录与撤销

#### P1-5 批量删除后“撤销”只能恢复最后一条
- 位置：`lib/providers/app_data/import_restore.dart:209-240`、`lib/providers/app_data/records.dart:342-411`
- 触发：在记录列表多选删除（`deleteRecords`）后点撤销。
- 后果：`deleteRecords` 在 `_batch` 内逐条调用 `deleteRecord()`，每条都覆盖 `_lastRecordUndo`，最终快照只含最后一条；`keepAttendance: true` 分支甚至完全不更新快照（残留上一次操作的旧快照，撤销可能回滚到无关操作）。
- 修复：`deleteRecords` 收集全部命中后一次性构造 `_RecordUndo.delete(hits)`。

#### P1-6 `addRecord` 的撤销快照晚于副作用，监听者在同步回调里撤销会回滚错
- 位置：`lib/providers/app_data/records.dart:119-122`
- 触发：新增一条命中“批评原因→考勤状态”映射的记录；`_applyRecordSideEffects` 触发 `_save()`/`notifyListeners()`，有监听者在回调里立即执行撤销。
- 后果：此时 `_lastRecordUndo` 还是上一条操作的快照，撤销会回滚到上一次操作。`updateRecord` 已有注释“快照必须先于任何可能通知界面的步骤”，`addRecord` 口径相反。
- 修复：把 `_lastRecordUndo = ...` 移到 `_applyRecordSideEffects` 之前。

### C. 考勤（开关打开后生效）

#### P1-7 手工登记的考勤被二次同步静默改写，并留下无来源的“考勤同步”记录
- 位置：`lib/providers/app_data_provider.dart:1680-1687`、`:1691-1707`
- 触发：老师手工登记“缺勤”（有映射）→ 系统自动建“考勤同步”批评记录并回填 `syncedRecordId` → 之后同一学生/日期/时段再录一条映射到“迟到”的批评记录。
- 后果：`syncedRecordId.isNotEmpty && list[index].syncedRecordId.isEmpty` 的保护不成立（值已被回填），手工考勤被静默改成“迟到”、关联被新记录抢走；原自动记录成为无来源，永久计入批评统计。
- 置信度：高（静态，代码路径完整）。

#### P1-8 编辑记录改时段撞键后，记录与考勤永久不一致
- 位置：`lib/providers/app_data_provider.dart:1299-1318`；`lib/providers/app_data/records.dart:246,256`
- 触发：编辑批评记录把时段从 A 改到 B，而该生 B 时段已有考勤（手工或派生）。
- 后果：记录已按 B 写库，`movePeriod=false` 使考勤保留在 A；`updateRecord` 只调 `_resyncRecordEdit`，不会重跑 `_syncAttendanceToRecords` → 记录显示 B、考勤统计/导出记在 A，永久不一致（仅一条内部日志）。
- 修复：撞键时要么回滚记录的时段变更，要么把记录时段改回 A 并提示用户。

#### P1-9 成功搬移时段时不更新 `periodName` 快照，界面/导出仍显示旧时段名
- 位置：`lib/providers/app_data_provider.dart:1322-1337`；`lib/models/attendance_record.dart:72-73`
- 触发：编辑记录并成功把考勤从 A 搬到 B。
- 后果：`copyWith` 只传 `periodKey`，`periodName` 仍是旧快照；`periodLabel` 优先用快照 → chip 分组键已变、导出“时间段”列仍打印旧时段名。
- 修复：搬移时同时写 `periodName: getTimePeriodName(effectiveKey)`。

### D. 导入 / 导出

#### P1-10 考勤表格导入静默丢弃“出勤”行与空行，且不计数

#### P1-11 原因库/时段 `.txt` 导入使用宽松解码，GBK 文件乱码静默入库

#### P1-12 整包还原不校验 `operationType`
- 位置：`lib/providers/app_data/import_restore.dart:439-457`

### F. UI / 更新

## 四、已验证无问题的关键路径

以下项目专门核对过，**不是**“没看”，而是确认当前实现正确（避免后续重复排查）：

1. **文件加密与密码存储**：LRX2 格式、salt/nonce 随机、HMAC 完整性校验、恒定时间比较、密钥未写入日志；文件头已诚实声明“加密不构成机密性保证”。注意：**文件加密的密钥派生是单次 SHA-256（内置密钥，属混淆级）**；PBKDF2 10 万次迭代是**登录密码存储**（`lib/services/security_service.dart`）用的，两者不要混为一谈；详见 7.4。
2. **原子写**：`AtomicFile` 按目标路径串行、临时文件 + flush + rename 重试、失败清理临时文件。
3. **保存队列**：`_pendingSave = task.catchError(...)` 防链停摆；`_batch` 的 `_suspendSaveDepth` 计数配对正确；`dispose` 后 `notifyListeners` 被拦截；只读接口返回 `List.unmodifiable`。
4. **考勤同步无死循环**：`_syncAttendanceToRecords` 新建记录时直接 `_recordsOf(date).add(_buildRecord(...))`，绕过 `_applyRecordSideEffects`，A→B→A 递归被截断。
5. **同键重复考勤**：`setAttendanceForStudents`、`importAttendance`、`_resyncRecordEdit` 都按 `学生+periodKey` 先 `indexWhere` 去重。
6. **学生改名**：同步更新 `attendanceByDate` 中的 `studentName`，不会产生“名单外学生”。
7. **更新校验**：SHA-256 真比对；无校验值直接取消更新；MSI 静默参数与含空格/中文路径转义正确；未发现“不校验直接安装”路径。
8. **Excel 公式注入**：全部单元格使用 `TextCellValue`，未发现 `=` 开头被当公式的路径。
9. **单实例**：原生 `CreateMutexW` + `FindWindowW` + `PostMessageW`，`--tray`/`--ball` 启动隐藏。
10. **AppSettings 序列化**：59 个字段 `toJson`/`fromJson`/`copyWith` 三处集合完全一致。
11. **统计并列名次**：`denseRanks` 与导出实现等价；`startOfWeek`、`datesBetween` 日历进位、`rangeDays` UTC 差、除零保护均正确。
12. **UI 资源释放**：`HeaderBar` 定时器、天气刷新、`main.dart` 的 timer/controller/focusNode 均在 dispose 释放并带 mounted 校验。

### 7.1 发布链路（安装包 / 升级 / 发布脚本）

#### P0-2 安装包没有携带 VC++ 运行库，干净系统首装后程序打不开（阻断首次安装）

- 位置：`installer/installer.iss:39`（`Source: "VC_redist.x64.exe" ... skipifsourcedoesntexist`）、`installer/installer.iss:47`（`[Run] ... skipifdoesntexist runhidden`）
- 依据（实测）：`build/windows/x64/runner/班级管理系统.exe` 的导入表明确依赖 `MSVCP140.dll`、`VCRUNTIME140.dll`、`VCRUNTIME140_1.dll`（`dumpbin /dependents` 实测）；但 `build/windows/x64/runner/` 目录只有 `flutter_windows.dll` 与三个插件 dll，**没有这三个运行库 dll**；`installer/` 与整个仓库也**没有 `VC_redist.x64.exe`**（`find . -iname "*vc_redist*"` 零命中）。`skipifsourcedoesntexist` + `skipifdoesntexist` 让安装程序在缺文件时静默跳过，安装仍显示成功。
- 后果：在一台没装过 Visual C++ 2015-2022 运行库的干净 Windows 10/11 上，安装成功但双击程序报“缺少 MSVCP140.dll”/`0xc000007b`，用户第一印象是“装了个坏的”。`README.md:78` 写“安装包已包含运行所需组件；如系统缺少 Visual C++ 运行库，安装程序会提示”，与实现矛盾。
- 修复建议：把 `VC_redist.x64.exe` 放进 `installer/`（源码注释本来就是这个意图），或在构建时把 `msvcp140.dll`/`vcruntime140.dll`/`vcruntime140_1.dll` 复制到 runner 目录随包分发；`release_check.py` 增加“VC_redist 文件存在且安装后程序能在无运行库环境启动”的断言。

#### P0-3 在线更新只传 `/SILENT /NORESTART` 且 `Start-Process -Wait` 无超时，安装器一弹框就永久卡住（阻断在线更新）

- 位置：`lib/services/update_launcher.dart:43-44`（EXE 分支 `-ArgumentList '/SILENT /NORESTART'`）、`:89-96`（`Start-Process ... -Wait -PassThru` 无超时；60 秒只用于等待主程序退出）
- 依据：Inno Setup 的 `/SILENT` 只隐藏向导，**错误对话框、权限提示、重启提示仍会弹出**；缺 `/SUPPRESSMSGBOXES`、`/SP-`、`/CLOSEAPPLICATIONS`。主程序已在更新前退出，PowerShell 的 `Start-Process -Wait` 会无限等待用户点击安装器上的按钮；用户看到的是“程序消失，再也不出来”。
- 后果：文件被占用、权限不足、需要重启等任一异常都会让更新流程永久悬挂；对普通用户等于更新失败后程序不可用，只能手工结束安装器进程再手工打开。
- 修复建议：线上参数改为 `/VERYSILENT /SUPPRESSMSGBOXES /NORESTART /SP- /CLOSEAPPLICATIONS /RESTARTAPPLICATIONS` 的组合并按真机验证；PowerShell 侧给 `Start-Process` 包一层超时（如 `Wait-Process -Timeout 180`），超时后记录日志、重新拉起原程序并提示。

### 7.4 加密强度实测

- 结构：LRX2 = `magic(4) + salt(16) + nonce(16) + cipher(N) + HMAC-SHA256 tag(32)`；`_encodeData` 每次 `Random.secure()` 生成 salt/nonce；`_keystream` 用 `HMAC-SHA256(encKey, salt|nonce|counter)` 逐 32 字节 XOR（CTR 模式）；`tag = HMAC-SHA256(macKey, body)` 为 encrypt-then-MAC，解密前恒定时间比较 tag。
- 临时探针（`test/audit_probe_crypto_tmp_test.dart`，已删除）实测：同一明文两次 `encodeLocalText` 密文不同（nonce/salt 随机）；翻转密文 1 字节后 `decodeRawForTest` 返回 `null`（篡改被拒）；原始密文可正常解回。
- 密钥派生：`_deriveKey(p) = SHA-256(utf8(p))`，是**单次哈希**，不是 PBKDF2；`_dataKey` 由程序内置两份 key share 异或得到，因此文件加密是**混淆级 + 防篡改**，不是机密性保护。`lib/services/storage_service.dart:56-65` 已如实写明“拿到 exe 的人可以逆出密钥并解开 .enc”。
- 注意区分：**密码存储**用的是 PBKDF2 10 万次迭代（`lib/services/security_service.dart`），与文件加密无关；主体报告“已验证无问题”第 1 条此前把两者混在一起，已在上文修正。未发现加密实现层面的算法错误。

### 7.5 大数据性能实测

- `flutter test test/big_data_smoke_test.dart`：2 个用例通过，总耗时约 3 秒；约 9,900 条记录统计 <10 秒断言通过、加密存盘→读回闭环完整。
- 临时探针：49,500 条记录（全班学生（人数已脱敏） × 900 条）执行 `StatisticsService.compute + attentionStudents` 耗时 **97ms**，表扬 39,600 / 批评 9,900 / 关注 55。相对真实数据 真实记录（计数已脱敏）有充足余量，**未发现性能瓶颈**。
- P3 提示：`_saveDataNow` 每次保存都会 `jsonEncode` 整份 `AppData` 并整文件重写；记录量到数万条后，频繁保存的 IO 成本会线性上升。当前 真实记录（计数已脱敏）无影响，若未来做“每键保存”需重新评估。

### 7.6 注册表 / 开机自启动 / 单实例
